# 情绪协议

智能体不使用状态名，而是使用两位数字的编号。

```json
{ "session_id": "s1", "aoraBotId": "34", "tips": "Build failed" }
```

shell hook 可以直接发出 `34`，不必知道另一端的角色把「出错」叫什么；状态名也可以随意改，不会弄坏按编号写的中继脚本。编号按十位分段，所以接收方即使没见过某个编号，也能大致判断它属于哪一类。

## 编号表

<ProtocolTable />

每一段里带下划线的编号，是该区间内未知编号的回退目标。标为*事件*的行描述的是一个瞬间，而不是一种持续的状况，见[事件与条件](#事件与条件)。

## 分段

| 区间    | 分段       | 回退 | 这里有什么                   |
| ------- | ---------- | ---- | ---------------------------- |
| `00–09` | 生命周期   | `02` | 睡眠、唤醒、待机、加载、关机 |
| `10–29` | 情绪       | `02` | 从开心到弹跳的各种心情       |
| `30–49` | 智能体工作 | `32` | 思考、检索、回复、完成、出错 |
| `50–59` | 提示       | `50` | 面向用户的警示与通知         |

落在所有分段之外的编号解析为待机。任何情况下都不会抛出错误：通道里的内容来自别人的脚本，一个笔误只应让角色降级显示，不能让它停摆。

```ts
stateForEmotion('34'); // 'alerting'
stateForEmotion('47'); // 'progress'
stateForEmotion('29'); // 'idle'      —— 未分配的情绪编号 → 分段回退
stateForEmotion('99'); // 'idle'      —— 所有分段之外
stateForEmotion(3); //    'curious'   —— 数字和单个数位会被归一化
```

## 编号永不重排

编号的数字和含义一经确定就不再改变，因为外面已有脚本在发送它们。每个十位段的空位里放的是 `03` 好奇、`09` 拖拽、`26` 弹跳、`27` 哼歌、`38` 拒绝，以及 `42`–`49` 更细分的工具状态，所以两位数始终够用，也没有任何编号改过含义。`09` 归在生命周期段，是因为被拿起来移动是发生*在*角色身上的事，不是一种心情；`27` 是一种情绪，指某件事自行顺利运转时的一点满足。

有些编号共用同一个状态：`15` *疲惫*和 `06` *休眠*都是困倦，`16` *专注*和 `32` *处理中*都是工作。这是有意的。编号记录的是发送方的本意，状态则是 Aora Bot 选择的呈现方式。`emotionIdForState` 返回某个状态对应的最小编号，基于 Aora Bot 的宿主应当发出这个编号。

## 事件与条件

大多数编号描述一种**条件**：智能体*正在*思考，*正在*检索。少数编号描述一个**事件**：智能体*完成了*，_出错了_，_被吓了一跳_。[仲裁器](/guide/agent-integration#仲裁)对两者的处理不同：事件会排队，并且一定会播放；条件在停留时间结束时重新解析，因为局面可能已经变了。

## 两种寻址方式

所有接受编号的地方也接受状态名，解析器对这两种写法都支持，可以是单独的字符串，也可以放在对象里：

```ts
parseAgentMessage('34'); //                     { emotionId: '34', state: 'alerting' }
parseAgentMessage('thinking'); //               { emotionId: '30', state: 'thinking' }
parseAgentMessage({ aoraBotId: 33, tips: 'ok' }); // { emotionId: '33', state: 'celebrate', tips: 'ok' }
parseAgentMessage('{"emotionId":"40"}'); //     { emotionId: '40', state: 'searching' }
parseAgentMessage('nope'); //                   null
```

React 组件可以用 `emotionId` 代替 `state`：

```tsx
<CharacterMark emotionId="30" />
<SpriteMark src="/sprites/bao/manifest.json" emotionId="33" />
```

## HUD

消息还可以带第三个可选字段：画在身体外那圈环上的表盘。

```json
{
  "session_id": "s1",
  "aoraBotId": "32",
  "tips": "Indexing 3 of 5",
  "hud": { "kind": "progress", "value": 0.6 }
}
```

`hud` 是一个 `HudSpec`，形如 `{ kind, ...fields }`。`kind` 取 `HUD_KINDS` 之一，其余字段由具体种类决定：`progress` 需要 `0..1` 范围内的 `value`，`timer` 需要 `remainingMs` 和 `totalMs`，`context` 需要 `used` 和 `total`，`voice` 需要 `level`。完整清单见 [HudPlate](/components/hud-plate) 页。

格式不合法的 `hud` 会被丢弃，消息的其余部分照常投递：消息里还带着状态信息，没有表盘也值得送达。而只对了一半的规格，例如没有 `value` 的 `{ "kind": "progress" }`，会画出一个空环，看起来像任务卡住了，而不像出了 bug。`isHudSpec` 是解析器使用的类型守卫，宿主也可以直接调用。

[仲裁器](/guide/agent-integration#仲裁)的结果里，`hud` 和 `tips` 并排携带，所以表盘跟随的会话和脸是同一个。

## 精灵图说同一种协议

[`SpriteMark`](/components/sprite-mark) 的清单用这些编号索引帧，缺失的编号走同一套分段回退。宿主可以把程序化绘制的角色换成手绘角色，状态逻辑完全不用改。
